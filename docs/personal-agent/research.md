# Muse / Grok Bot 产品调研

2026-10-27已补充[Grok Bot功能逐项对照](grok-functional-reference.md)与[产品设计v0.2](product-design-v02.md)，包括官方功能链接与本产品的实现选择。下文保留首轮调研。

截至 2026-10-26，本文中的 Muse 指 Meta 的 personal agent，Grok Bot 指 xAI / Cursor 的持久 Bot 产品，不等同于 Grok 聊天模型或 `grok` CLI。证据来自官方产品页和技术文档；未登录两款产品完成端到端任务，也没有留存率、成功率或延迟测量。“体验为什么好”以下是由交互机制推导的解释，不是已证明的因果关系。

## 1. 已核实的产品组织

| 维度 | Muse | Grok Bot | 对本项目的启发 |
| --- | --- | --- | --- |
| 用户认识的对象 | 一个了解自己的个人助理 | 有名字和分工的多个 Bot | 默认一个助理，任务变复杂后再增加专长 |
| 起点 | 用消息描述目标 | 创建 Bot 后描述工作 | 不要求用户先搭建工作流 |
| 执行位置 | 独立云端计算环境，Mac 可扩展本机能力 | 账号拥有的持久云端电脑 | 客户端与执行节点分离 |
| 连续性 | 后台推进，记住相关信息 | 跨会话保留角色、文件与上下文 | 对话是长期关系，任务是可验收交付 |
| 控制入口 | 查看活动，按连接设置权限 | 任务中途审批、浏览器接管 | 把中断放回原任务，不另开设置迷宫 |

Muse 的消息入口、后台任务与个人信息记忆见 [Meta 发布说明](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/amp/)。Mac 读取文件和应用的定位见 [官方下载页](https://ai.meta.com/muse/download/)。Grok Bot 的身份、跨端、持久电脑与上下文见 [Overview](https://docs.x.ai/grok-bot/overview)。

## 2. 好体验来自哪些具体机制

**把配置成本延后到真实任务。** 用户先表达“整理研究并留一份草稿”，系统在需要某项数据或工具时再提出连接。第一次交付提供继续配置的理由。推导：成功的起点应是一个小而有用的结果；一屏权限和模型配置会提前消耗信任。

**稳定身份减少重复交代。** 名字、任务历史和可检查的记忆使后续交互有连续性。记忆若不暴露来源和修改方式，也会把错误长期化。设计不能把“能记住”直接等同于“了解用户”。Grok Bot 对记忆与共享文件的说明见 [Bots 概览](https://docs.x.ai/grok-bot/overview)。

**后台执行把等待改为交付。** 客户端退出后，任务仍可由在线执行节点推进。通知只在结果变化或需要处理时出现。代价是后台任务必须有持久状态、恢复策略和明确的执行位置。官方云端工作模型见 [Computer and apps](https://docs.x.ai/grok-bot/computer-and-apps)。本地 Mac 睡眠时不具备相同保证。

**工作过程可见，但默认不展示调试流。** 用户关心正在做什么、为什么卡住、何时需要自己。对话中的阶段反馈与成果入口比原始工具日志更适合作为默认反馈。官网展示的示范学习与记忆更新是产品表达，不能当成可靠性测量：[Grok Bot 展示](https://x.ai/bot)。

**复用已成功的方法。** Grok Bot 区分 skill（做法）和 routine（触发时间），推荐先把单次任务做可靠再自动化。这减少了最初学习工作流编辑器的负担，也让自动化有可回溯的前例：[Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)。

## 3. 信任是交互基础设施

Muse 官方架构把执行与授权分开，由独立 Sentinel 管理连接器调用和网络出口，真实凭证也与执行环境分离。这里值得学习的是“执行者不能自行扩大授权”的边界，而不是再加一段要求模型谨慎的提示词。该说明也明确系统仍会犯错：[安全架构说明](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)。

Grok Bot 提供审批与敏感输入接管；同一账号多个 Bot 共享电脑和登录态，因此 Bot 分工并不构成文件权限隔离：[审批与隐私](https://docs.x.ai/grok-bot/approvals-security-and-privacy)、[电脑模型](https://docs.x.ai/grok-bot/computer-and-apps)。本项目应明确区分“给 Agent 一个工作目录”和“限制 Agent 访问范围”。

## 4. 不能直接复制的部分

云端电脑、持续在线资源、连接器维护和模型对长任务的适配共同支撑体验。仅复制聊天布局无法复制结果质量。跨端入口也不意味着所有端都能执行：手机可发起和审批，Mac 可能是唯一执行节点。

一个反例是 Agent 显示“已安排”，但执行电脑正在睡眠；另一个是 UI 显示“需审批”，原生 runtime 却能通过 shell 绕过它。因此本项目的一期验收必须包括断线、恢复、发送结果未知与权限撤销，不能只检查首页是否漂亮。

## 5. 后续实测协议

对两款产品使用相同的三类任务：公开资料研究并产出文档；整理一个专用测试目录；由用户连接测试日历后提出事件草稿。分别记录首次成果耗时、主动追问次数、重复提供背景次数、用户接管时长、错误恢复路径和最终可用成果比例。

每类任务至少重复五次；记录产品版本、任务文本、权限、执行节点与原始结果。先完成只读研究，再测试外部写操作。不用官网演示或单次成功为“很好用”背书。当前没有这批测量数据。
